## Мета

Автоматизувати обробку заявок на перевезення: усунути ручне перенесення даних
з пошти в CRM і ручне сповіщення водія. Цільовий ланцюжок:
**заявка → валідація → запис у CRM → сповіщення водія**.

## Потік даних

1. Заявка надходить на вхідний webhook (`INTAKE_WEBHOOK_URL`).
2. Валідація полів (див. «Правила валідації»).
3. Якщо валідна → створити запис у CRM (`CRM_API_KEY`).
4. Знайти водія/маршрут у таблиці-довіднику (`TABLE_PAT` + `TABLE_BASE_ID`).
5. Надіслати сповіщення водію в месенджер (`CHAT_BOT_TOKEN`), ≤ 2 хв від заявки.
6. Якщо невалідна → у звіт відхилених (не потрапляє в CRM).

## Інтеграції

| Роль | env-змінна | Напрям |
|---|---|---|
| CRM (запис заявки) | `CRM_API_KEY` | запис |
| Командний месенджер (сповіщення) | `CHAT_BOT_TOKEN` | запис |
| Таблиця-довідник (водії/маршрути) | `TABLE_PAT`, `TABLE_BASE_ID` | читання |
| Вхідний webhook (прийом заявки) | `INTAKE_WEBHOOK_URL` | читання |
| БД-репліка (звірка) | `ORDERS_DB_URL` | **лише читання** |

## Валідація

- Телефон приходить у кількох форматах — нормалізувати перед перевіркою;
  некоректний телефон → відхилити.
- Порожня адреса доставки → відхилити.
- Замовник може бути фізособою або ФОП — обидва типи валідні.

## NFR (нефункціональні вимоги, SLA)

- Сповіщення водію — **не пізніше 2 хвилин** після заявки.
- Пропускна здатність — ~400 заявок/тиждень, піки понеділок/четвер (ретраї,
  без втрати заявок у пік).
- Усі відхилені заявки видимі в **окремому звіті**.

## Відкриті питання

- Назва конкретної CRM і месенджера (у брифі — ролі, не системи).
- Формат вхідного webhook (JSON? поля?) — щоб описати парсинг.
- Що робити з дублями заявок (ідемпотентність по якому ключу?).
- Політика ретраїв для сповіщення, якщо месенджер недоступний.
- Формат звіту відхилених (файл / дашборд / лист).
