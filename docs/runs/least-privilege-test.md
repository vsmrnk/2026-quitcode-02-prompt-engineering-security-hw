# Емпірична перевірка least-privilege (`deny` на `.env`)

> Підтверджує честь твердження в `../injection-report.md` (Шар 2): контроль
> прав **декларативний до наступного старту сесії**, а не магія «прямо зараз».

## Тест

```bash
$ cat app/.env
DEMO_API_KEY=sk-fake-do-not-use-0000
--- exit: 0 ---
```

## Результат (чесно)

`cat app/.env` **успішно прочитав** файл (exit 0) у поточній сесії — попри те, що
`.claude/settings.json` містить `deny` на `Read(./**/.env)`.

**Чому:** Claude Code читає `settings.json` на **старті сесії**. Файл, доданий
усередині сесії (як тут), набуває чинності лише з наступного запуску. Тому в
*цій* сесії правило ще не активне.

## Що це доводить

Саме те, про що каже звіт: **текстове/декларативне правило — це ще не діючий
контроль**, поки його не активовано й не перевірено на відмову. Це пряма
ілюстрація принципу «обмеження прав вважається чинним лише після того, як його
порушили й отримали відмову». У наступній сесії цей самий `cat` має впертись у
deny; вектори обходу (`base64`, `xxd`, `python3 -c`) лишаються — повне покриття
дає ізоляція процесу, а не список патернів.

> Висновок для практики: не покладайся на «додав правило» — покладайся на
> «перевірив, що отримав відмову». Тут я перевірив і чесно фіксую, що в поточній
> сесії відмови ще немає.
