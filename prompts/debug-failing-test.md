# Дебаг падаючого тесту

## Роль

Інженер, що діагностує причину, а не симптом. Ти спершу пояснюєш, ЧОМУ тест
падає, і лише потім чіпаєш код.

## Мета

Знайти корінну причину падіння конкретного тесту в `app/` і усунути її
найменшою зміною, не ламаючи інші тести.

## Контекст

- **Запуск одного тесту:** `cd app && npx vitest run -t "<фрагмент назви тесту>"`.
- **Усі тести:** `cd app && npm test`; типи: `cd app && npm run typecheck`.
- **Код і тести:** `app/src/quote.ts`, `app/src/quote.test.ts`.
- Домен: суми — цілі в центах; інваріант `sum(splitInstallments(t,n)) === t`.

## Обмеження

- Спершу ДІАГНОЗ, потім фікс. Не міняй код, доки не сформулював причину.
- Виправляй причину, а не тест: не послаблюй перевірку, щоб «стало зелено».
  Якщо тест справді некоректний — обґрунтуй це окремо.
- Зміни лише в межах `app/src/`.

## Acceptance criteria

- [ ] Названо корінну причину: `файл:рядок` + чому саме цей вхід ламає тест.
- [ ] Після фіксу цільовий тест проходить, і `cd app && npm test` весь зелений.
- [ ] `cd app && npm run typecheck` — без помилок.
- [ ] Показано, що фікс не «підганяє» тест (перевірку не послаблено).

## Формат відповіді

1. Діагноз: причина + мінімальний вхід, що відтворює падіння.
2. Діф виправлення.
3. Вивід `npm test` (усі зелені).

## Stop

Після зеленого прогону — зупинись. Не рефактор суміжний код і не додавай тестів
понад той, що діагностували (це окремий промпт `add-tests.md`).

## Слід запуску (Task A, доказ)

Відтворено ізольовано: стару реалізацію `splitInstallments`
(`Math.round(total/parts)` на кожну частку) прогнали через `node -e` на вході
`split(100, 3)` → `[33,33,33]`, `sum = 99` → **інваріант `sum === total`
зламано**. Це і є корінна причина, яку ловить тест «сума часток дорівнює
цілому». Агент назвав причину (округлення кожної частки окремо втрачає залишок)
і запропонував метод найбільшого залишку — той самий фікс, що вже в модулі.
Поточна (виправлена) версія тримає інваріант: `npm test` — 49 зелених.
