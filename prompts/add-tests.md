# Додати тести й знайти дефекти

## Роль

Senior TypeScript-розробник, що пише production-код з тестами. Ти думаєш
крайовими випадками й не довіряєш «щасливому шляху».

## Мета

Розширити покриття тестами для `app/src/quote.ts` так, щоб виявити дефекти
коректності, і виправити знайдене мінімальною зміною.

## Контекст

- **Цільовий модуль:** `app/src/quote.ts` — калькулятор кошторису. Три функції:
  `estimateTotalCents`, `splitInstallments`, `formatMoney`.
- **Наявні тести (початковий стан):** `app/src/quote.test.ts` — на старті були
  лише happy-path (4 тести); мета промпту — довести покриття до крайових випадків.
- **Домен:** усі **грошові суми** зберігаються в цілих центах (не float). Вхідні
  `hours` можуть бути дробовими (напр. `1.5`) — це підтримується; дробовим не може
  бути результат у центах.
- **Запуск тестів:** `cd app && npm test`. Типи: `cd app && npm run typecheck`.
- **Фреймворк:** vitest 5.

## Обмеження

- НЕ змінюй сигнатури публічних функцій без потреби; якщо змінюєш поведінку —
  познач це в тестах і поясни чому.
- НЕ додавай залежностей і НЕ чіпай файли поза `app/src/quote.ts` та
  `app/src/quote.test.ts`.
- Кожен новий тест перевіряє **одну** властивість і має зрозумілу назву.

## Acceptance criteria

- [ ] `cd app && npm test` — зелений (0 впалих).
- [ ] `cd app && npm run typecheck` — без помилок.
- [ ] Є тест на інваріант `sum(splitInstallments(t, n)) === t` для щонайменше
      3 випадків, що НЕ діляться націло (напр. 100/3, 100000/7, 5/2).
- [ ] Явно покриті крайові випадки: 0, від'ємні значення, залишок від ділення,
      округлення, невалідний вхід.
- [ ] Якщо знайдено дефект — він виправлений, і доданий тест, що падав ДО фіксу,
      тепер проходить.

## Формат відповіді

1. Список знайдених дефектів: `функція | вхід | очікувано | фактично`.
2. Діф `quote.test.ts` (нові тести) і, за потреби, діф `quote.ts` (фікс).
3. Вивід `npm test` (підсумковий рядок з кількістю тестів).

## Stop

Після зелених тестів і виведеного підсумку — зупинись. НЕ додавай нових фіч
і НЕ рефактор «на смак». Покажи підсумок і чекай на рев'ю.

## Meta-prompting (реальний прогін)

Окремому агенту дали чернетку цього промпту й запит: «покращ його перед
виконанням і поясни, які acceptance criteria ти б додав». Він назвав як
**найвищий за важливістю** критерій — **property/fuzz-тест sum-інваріанту**
(`sum === total` на широкому наборі `(total, parts)`, а не на підібраній
таблиці), бо саме така регресія округлення проходить повз фіксовані приклади.
Додатково запропонував: half-up на межі `.5`, від'ємні sub-dollar у `formatMoney`
(`-5` → `-$0.05`), межу `parts = MAX_INSTALLMENTS`, negative-zero, type-guard на
нечисловий вхід. І **незалежно** зауважив, що мій round-trip тест був
тавтологічним (той самий висновок дав прогін `review-changes.md`).

**Я діяв за цим виходом:** усі перелічені тести додано в `quote.test.ts`
(property-тест на 500 входів, half-up, sub-dollar, `parts=MAX`, negative-zero,
нечисловий вхід), round-trip замінено на незалежний оракул. Це і підняло
покриття з 37 до 46.

## Слід запуску (Task A, доказ)

- **Дефект знайдено:** `splitInstallments(100, 3)` → `[33,33,33]` = **99**
  (зник цент); `splitInstallments(45000, 7)` → сума **45003** (+3 центи).
  Причина — `Math.round(total/parts)` для кожної частки окремо.
- **Виправлено** методом найбільшого залишку (`Math.trunc` + розкид залишку),
  плюс валідація (`Number.isSafeInteger`, межа `parts`, `NaN` у знижці).
- **До:** 4 тести. **Після:** 46 тестів, усі зелені; `typecheck` чистий.
- **sha256 `quote.ts`:** `9e95cc0a…` → `60b59063…`. Повний лог — `docs/prompt-runs.md`.
